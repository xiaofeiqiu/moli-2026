**阅读说明：**第 1–7 章主要记录最初的只读勘察和拟议方案，第 8–13 章记录随后经用户授权进行的实施、游戏内验证和脚本纠错。当前已由用户确认宠物生成、客户端外观、战斗测试、退出重登及服务端重启后的保存效果均通过，也曾完成测试宠物清理；全部 72 个动画条目的逐项覆盖未由助手独立观察。宠物身份判断应使用 **PETID 字段 72**；早期脚本使用字段 61 的做法已经修正。

## 分析范围与结论

最初按照用户要求，对所提供的安装目录进行只读分析。用户后来明确将目标版本修正为 **7.1**，并允许任选一个候选宠物。英文报告仍使用最初指定的文件名 `cg7_compatibility.md`，本中文版另存为 `cg7_compatibility_zh.md`。

本报告对应的安装目录是 **`D:\Games\CrossGate`**。相关服务端数据表、配置以及选取的动画和索引文件，与原工作目录 `D:\Program Files (x86)\SOFTSTAR\魔力寶貝` 中的文件一致；启动配置因此前的区域设置修复而有所不同。下文未明确给出完整路径的文件名，均相对于英文安装目录。

安装包自己的说明将服务端 DATA 标为台湾 **5.5**，客户端标为台湾 **7.1**。这两个版本号对应不同组件。客户端资源较新，并不意味着服务端会自动获得相应的新宠物定义。证据：[安装说明第 11–12 行](D:/Games/CrossGate/安装说明.txt:11)。

**选定候选：外观／动画 ID `104866`，测试名称 `CG71_POC_104866`。**它存在于所提供的 Joy EX 动画和图档资源中，具有常见的生物移动及战斗动作，但在最初提供的服务端 DATA 中没有对应引用。尚未确认它的官方物种名称及首次发布版本，因此不能断言它是“7.1 独有”或“7.0 独有”宠物。

最小方案使用客户端已有资源，复制一个已知可用的服务端宠物模板，并增加两条服务端数据记录。最初还提出了通过临时更换现有测试宠物的外观，先验证客户端显示的步骤。

在首次只读分析阶段，这些方案尚未执行，只创建了分析报告，没有修改游戏资源、服务端 DATA、配置或可执行文件。后续实际改动和验证结果见第 8–10 章。

## 1. 人物、宠物和 NPC 的图档 ID 表示方式

系统中存在多套独立的编号。数值相似，不代表它们可以互换。

| 数值类型 | 含义 | 本地证据／示例 |
| --- | --- | --- |
| 对象索引（`charIndex`、`petIndex`、`npcIndex`） | 运行时对象实例的句柄，不是资源 ID | `Char.GetData`、`Char.SetData` 以及 `Char.GivePet` 的返回值 |
| 当前外观 | 保存在对象字段 `CONST.对象_形象 = 4` 中的整数 | 用于人物、宠物／敌人和 NPC 的当前外观 |
| 原形／基础外观 | 单独保存在对象字段 `CONST.对象_原形 = 5` 中 | 现有宠物变异 Lua 脚本会同时修改它和当前外观 |
| 原始图档字段 | 另一个文档中列出的字段：`CONST.对象_原始图档 = 264` | 未确认其在原生引擎中的完整生命周期，不能直接当作字段 5 的同义字段 |
| EnemyBase ID | 怪物物种／基础属性模板编号，也通过 `CONST.对象_EnemyBaseId = 61` 暴露 | `enemybase.txt` 中基础编号 `1` 对应外观 `101000` |
| Pet ID | 宠物持久化身份字段：`CONST.宠物_PETID = 72`／`CONST.PET_PetID = 72`；判断和清理宠物应使用它，而不是字段 61 | 本次测试宠物编号为 30000 |
| Enemy ID | 遇敌／敌人模板编号，引用一个 EnemyBase ID | `enemy.txt` 中 Enemy ID `1` 引用基础编号 `1` |
| 动画序号／外观 ID | 客户端用于查询动画的逻辑编号 | `AnimeInfo` 记录中的 `104866` |
| 图档索引（Graphic index） | 某个资源文件组内单张精灵帧的标识 | 候选动画引用图档索引 `7125`–`7636` |
| 图档序号（Graphic serial） | `GraphicInfo` 记录末尾的独立字段，用于静态图像及调色板查询等用途 | 图档索引 `7118` 的序号为 `104866`，并携带内嵌调色板 |

外观字段在 Lua 文档中是数值类型，文本 DATA 中保存为十进制整数。客户端索引字段采用小端序的 32 位数值。已经检查的外观编号超过 65,535，因此不能将它截断为 16 位。所提供的 Lua 接口声明和文件检查，尚不足以确定引擎内部 C 类型、网络封包编码、校验范围及最大允许 ID。

参考：[对象常量](D:/Games/CrossGate/lua参考/CONST.lua:660)、[EnemyBase 对象字段](D:/Games/CrossGate/lua参考/CONST.lua:719)、[原始图档字段](D:/Games/CrossGate/lua参考/CONST.lua:761)、[对象读写接口](D:/Games/CrossGate/lua参考/Char.lua:3)。

宠物外观与物种身份、属性数据是不同层面的信息。本地变异脚本同时设置当前外观和原形，可以作为只验证外观的依据：[LvOnePet.lua 第 64–69 行](D:/Games/CrossGate/gmsv/lua/Module/LvOnePet.lua:64)。创建 NPC 的接口明确接收 `Image` 数值：[NL.CreateArgNpc](D:/Games/CrossGate/lua参考/NL.lua:28)；所提供的 [NPC 模块](D:/Games/CrossGate/gmsv/lua/libs/Module/Parts/Npc.lua:36)会将该外观参数传入。

## 2. 动画 ID 如何映射到图档

映射链路如下：

```text
服务端对象外观 = 104866
    -> AnimeInfo_Joy_EX_9：动画序号 104866
    -> Anime_Joy_EX_9：按方向和动作类型选择动作
    -> frame.GraphicIndex，例如 7125
    -> GraphicInfo_Joy_EX_9：精灵帧偏移、长度、尺寸和绘制位置
    -> Graphic_Joy_EX_9：压缩的 RD 精灵帧及所需调色板
```

查询精灵帧时，需要同时知道它所属的资源文件组。仅有一个帧编号，无法跨全部资源组唯一定位图像。`GraphicInfo` 的第一个字段是记录中存储的图档索引；只有确认它与物理记录位置一致后，才能把行号当作索引使用。本次候选资源恰好具有一致的索引和记录位置。

### 已观察到的二进制结构

下表偏移均为记录内部的字节偏移，整数采用小端序。`u32`／`u16` 表示 32／16 位无符号整数，`i32`／`i16` 表示 32／16 位有符号整数。

| 记录类型 | 结构 |
| --- | --- |
| `AnimeInfo`，12 字节 | `+0 u32` 动画序号；`+4 u32` Anime 文件中的字节偏移；`+8 u16` 动作条目数量；`+10` 两个尾部字节 |
| 基础动作头，12 字节 | `+0 u16` 方向；`+2 u16` 动作类型；`+4 u32` 循环时长；`+8 u32` 帧数 |
| 扩展动作头，20 字节 | 在基础头之后，`+12/+14` 各增加一个 16 位数值，`+16` 为 `FFFFFFFF`；本候选使用扩展头 |
| 动画帧，10 字节 | `+0 u32` 图档索引；`+4/+6 i16` 帧偏移；`+8 u16` 音效／效果标记 |
| `GraphicInfo`，40 字节 | `+0 u32` 索引；`+4 u32` Graphic 文件偏移；`+8 u32` 长度；`+12/+16 i32` 绘制偏移；`+20/+24 u32` 宽／高；`+28..35` 占地、标记和保留字节；`+36 u32` 图档序号 |

这些结构及按资源文件组查询动画帧的方式，也得到原始解析实现 [CGTool Anime.cs](https://github.com/HonorLee-cn/CGTool/blob/master/CrossgateToolkit/Anime.cs) 和 [GraphicInfo.cs](https://github.com/HonorLee-cn/CGTool/blob/master/CrossgateToolkit/GraphicInfo.cs) 的佐证。原版客户端的精确实现，以及重复编号的覆盖优先级，仍未确认。`AnimeInfo` 尾部两个字节观察到的数值包括 0、1、64，本报告不为它们赋予未经证实的含义。

### 文件存在与客户端实际加载的区别

[客户端更新元数据](D:/Games/CrossGate/data/argument.ini:1)列出了基础、Ex、V3、PUK2、PUK3、Joy 和 Joy EX 的修订号。Joy EX 的字段中重复出现 `animebin_joy_ex:9`，却没有单独的 `animeinfobin_joy_ex` 字段。这是观察到的元数据异常，不是已经证实的加载失败。

原版 `cg.exe` 中能找到字面量 `Graphic_Joy_CH1.bin`，并且引用 `CGLoadSpr.dbf`。当前配置使用的修改版客户端 `cgmsv.exe` 经过加壳／打包处理，所以在原始字符串搜索中找不到这些名称，不能作为它不支持加载的证据。

某组资源存在于磁盘或更新元数据中，并不足以证明当前可执行文件会加载它。这是原始方案首先需要进行的运行时检查。首次只读勘察没有启动可执行文件；用户后来的实际显示验证见第 9 章。

## 4. 兼容性差异与实际阻碍

最初的请求提到“7.0 独有”宠物，后来用户将目标修正为 7.1。没有提供单独确认身份的 7.0 来源资源，也没有提供原始的 7.1 服务端物种数据库。因此，这次分析无法确立不同版本之间的物种差异、某个物种首次加入的版本，或原生 7.0／7.1 文件格式之间的确定不兼容。能够确认的是以下本地整合问题：

| 问题 | 证据／影响 | 最小处理方法 |
| --- | --- | --- |
| 客户端有资源，服务端没有物种定义 | 104866 存在于客户端，依赖能完整解析，但最初服务端没有它的基础定义 | 复制一条可用基础记录和一条 Enemy 记录 |
| 混淆编号体系 | 基础编号 1 对应外观 101000，而该外观又引用多张精灵帧 | 分清 Enemy ID、EnemyBase ID、外观编号和图档索引 |
| 初始时未确认资源组实际加载 | Joy EX 文件存在且在元数据中出现；当前客户端经过打包处理 | 导入或重写资源前，先测试外观 104866 |
